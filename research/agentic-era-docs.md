## 2. Findings per topic

### 2.1 AGENTS.md and the tool-specific instruction files

**AGENTS.md (S1, S2).** Plain Markdown, no schema, no required fields or headings. Suggested content: project overview, build and test commands, code style, testing instructions, security considerations, plus commit/PR guidelines and deployment steps. Precedence rule stated by the site: the AGENTS.md nearest to the edited file wins, and an explicit user prompt overrides everything. The site says listed test commands will be run by agents. Governance: released by OpenAI in August 2025, donated on 2025-12-09 to the Agentic AI Foundation (a Linux Foundation directed fund co-founded by Anthropic, Block and OpenAI); the site footer reads "AGENTS.md a Series of LF Projects, LLC". Adoption claim: more than 60,000 open-source projects (a GitHub search count, not an audited number). Supporting tools listed on the site: Codex, Jules, Factory, Aider, goose, opencode, Zed, Warp, VS Code, Devin, UiPath, Junie, Amp, Cursor, RooCode, Gemini CLI, Kilo Code, Phoenix, Semgrep, GitHub Copilot coding agent, Ona, Windsurf, Augment Code. Claude Code is not on the site's list but reads AGENTS.md natively as of v2.1.277 (S3). Migration tip from the site: keep one real file and symlink the legacy name.

**How each tool actually loads files (important for a checker, because the rules differ).**

| Tool | Files read | Nesting and precedence | Size limits | Imports |
|---|---|---|---|---|
| Codex (S8) | `~/.codex/AGENTS.override.md` or `AGENTS.md` (first non-empty), then per directory from repo root down to cwd: `AGENTS.override.md`, `AGENTS.md`, then configured fallback names; at most one file per directory | Concatenated root to leaf; later (closer) text overrides; built once per run | Combined cap `project_doc_max_bytes` = 32 KiB by default; once reached, later files are silently dropped; empty files skipped | None documented |
| Claude Code (S3) | Managed, user (`~/.claude/CLAUDE.md`), project (`./CLAUDE.md` or `./.claude/CLAUDE.md`), `CLAUDE.local.md`, `.claude/rules/*.md`; AGENTS.md read only when no CLAUDE.md / CLAUDE.local.md exists in cwd or above (default mode `claude-md-or-agents-md`) | Ancestors loaded at start, broadest first; subdirectory files loaded lazily when a file there is read; conflicting instructions are resolved arbitrarily, no override semantics | Target under 200 lines per file ("longer files consume more context and reduce adherence"); auto memory loads first 200 lines or 25 KB | `@path` imports, relative to the importing file, max depth 4 hops, skipped inside code spans/blocks; imports do not reduce context cost; imports outside the project need a one-time approval |
| GitHub Copilot (S5) | `.github/copilot-instructions.md`; `.github/instructions/*.instructions.md` with `applyTo` globs; any `AGENTS.md`; a single root `CLAUDE.md` or `GEMINI.md` | Personal over repository over organisation, all supplied; nearest AGENTS.md wins; code review reads instructions from the PR head branch | No hard limit stated; the official onboarding prompt asks for at most 2 pages | None |
| Cursor (S6) | `.cursor/rules/*.mdc` (plain `.md` there is ignored), AGENTS.md in root and subdirectories, user and team rules | Team over project over user; nested AGENTS.md combined with parents, more specific wins | Keep each rule under 500 lines | Reference files rather than copy them |
| Gemini CLI (S7) | `~/.gemini/GEMINI.md`, workspace and parent `GEMINI.md`, just-in-time files in directories touched by tools; `context.fileName` can list `AGENTS.md` | All found files concatenated and sent with every prompt | None stated | `@file.md` |

Notable Claude Code details useful for rules: block-level HTML comments in CLAUDE.md are stripped before injection (free maintainer notes); `AGENTS.local.md`, `AGENTS.override.md` and `.agents/` are not read by Claude Code; adding a `CLAUDE.local.md` silently stops AGENTS.md from loading in the default mode; a `CLAUDE.md` containing only `@AGENTS.md` remains a safe portability shim and is never double-loaded; `/doctor prompt-audit` checks instruction files for dead file/command references, contradictions and instructions written for older models.

**What belongs in the agent file, per vendors.** Anthropic (S3, S4): only what the agent cannot work out from the code; commands for the checks it should run; keep it short; do not describe architecture and file layout ("Claude reads the repo itself"); do not add IMPORTANT/ALL CAPS emphasis (causes over-application; if a rule cannot bend, make it a hook or deny rule); personal preferences go in an untracked local file; procedures go in skills, which cost only a name and description until used. Instructions are "context, not enforced configuration". GitHub (S5): summary of the repo, languages and runtimes; bootstrap/build/test/run/lint commands with tool versions and step order; commands that were validated, known errors and workarounds; project layout and config file locations; CI checks; tell the agent to trust the instructions and search only when they are incomplete; no task-specific content. GitHub blog (S9): commands with flags near the top; one real code example beats paragraphs; six areas (commands, testing, project structure, code style, git workflow, boundaries); three-tier boundaries (always / ask first / never); exact stack versions; grow the file by iteration when the agent makes a mistake. Cursor (S6): add a rule only when the agent repeatedly makes the same mistake; do not copy style guides or duplicate what the codebase already shows.

**Relation to README and CONTRIBUTING.** AGENTS.md is positioned as the place for agent-relevant detail that would clutter a human README (S1). The ETH study (E1) found LLM-generated context files mostly duplicate existing documentation and only helped when the other docs were removed, and it recommends limiting human-written files to requirements not already in the README. In the wild, however, "contribution guidelines" is the second most frequent AGENTS.md heading category (48 headings, behind conventions with 50) (E4), so duplication with CONTRIBUTING is common practice. The sources converge on: single source of truth in README/CONTRIBUTING, agent file links or imports rather than restates, and one canonical agent file with thin shims for other tools (E5 observed 301 references from CLAUDE.md to AGENTS.md across 2,586 repos, and CLAUDE.md is usually created first with AGENTS.md added later).

### 2.2 Empirical evidence on context files

**Do they help? (E1).** Setup: SWE-bench Lite (300 tasks, 11 Python repos, no context files) and a new benchmark of 138 instances from 12 Python repos that have developer-committed context files (built from 5,694 PRs; named CTXbench in the v3 text read here, while secondary write-ups of v1 call it AGENTbench: naming discrepancy `unverified`). Agents: Claude Code (Sonnet 4.5), Codex (GPT-5.2, GPT-5.1 mini), Qwen Code (Qwen3-30B-coder); one run per instance. Results: LLM-generated files changed success by about -0.5 points (SWE-bench Lite, p = 0.87) and about -2 points (new benchmark, p = 0.37), neither significant; developer-written files gave about +2.4 points (p = 0.21, not significant) but significantly beat LLM-generated ones (p = 0.038). Cost rose about 20% and 23% with LLM-generated files and up to 19% with developer files; steps rose by about 2.5 to 3.9. Agents obey the files: `uv` was used about 1.6 times per instance when mentioned versus under 0.01 otherwise; repo-specific tools about 2.5 versus under 0.05; agents ran more tests and read more files. Codebase overviews (present in 8 of 12 developer files and in 95 to 100% of files generated by the stronger models) did not reduce the steps needed to reach the relevant files. With all other documentation removed, LLM-generated files improved success by about 2.7% and beat developer files, which the authors read as evidence of redundancy. No clear correlation between file length and success or cost; stronger models did not write better files. Authors' advice: skip LLM-generated files for now, keep human files to minimal non-inferable requirements, and evaluate before adopting. Caveats: Python only, small samples, django dominates SWE-bench Lite, only success/steps/cost measured (not security, style conformance or maintainability, which are what many instructions target), and the success differences are not statistically significant in either direction.

**Efficiency (E2).** On 10 repos and 124 PRs, presence of AGENTS.md was associated with 28.64% lower median wall-clock time and 16.58% lower output tokens with comparable completion. Caveats: correlational wording, small sample, output tokens only, abstract only read. This conflicts in direction with E1's cost increase; the two differ in tasks, metrics (output tokens vs total cost) and files used.

**What files contain (E3, E4, E5).** E3 (2,303 files, 1,925 repos; 922 CLAUDE.md, 694 AGENTS.md, 687 copilot-instructions): share of files covering testing 75.9%, implementation details 70.8%, architecture 68.1%, development process 65.1%, build and run 63.0%, system overview 59.0%, maintenance 44.6%, configuration 38.9%, documentation references 26.8%, debugging 25.3%, security 14.8%, performance 14.5%. Median length 335.5 words (AGENTS.md), 485 (CLAUDE.md), 535 (Copilot). Median Flesch Reading Ease 42 to 51 ("difficult"), though the authors note this partly reflects technical vocabulary and lists. Median 1 H1, 6 to 7 H2, 9 to 12 H3. E4 (466 of 10,000 repos, about 5%, had a context file; 155 AGENTS.md analysed): mean length 142 lines for AGENTS.md (SD 231), 287 for CLAUDE.md, 310 for Copilot instructions, 106 for GEMINI.md; no established structure; five writing styles (descriptive, prescriptive, prohibitive, explanatory, conditional); security appears in only 6 headings. E5 (2,853 repos, Feb 2026 snapshot): context files in 90.6% of configured repos; file shares CLAUDE.md 34.4%, AGENTS.md 31.6%, copilot-instructions 29.2%, GEMINI.md 3.2%, `.cursorrules` 1.5% (deprecated); skills in about 5.5% of repos, subagents in about 4.6%.

**Maintenance and staleness (E3, E4, E6, E7).** The two descriptive studies disagree on cadence because of sampling: E4 found 50% of AGENTS.md files never changed after creation and only 6% had 10 or more commits; E3 found 59 to 67% of files modified in more than one commit, with a median 22 to 68 hours between updates, edits being mostly small additions (median 57 words added, under 15 deleted), i.e. files grow and are rarely pruned. E7: 23.0% of 356 sampled repos contain stale code-element references in their AI config files (preliminary). E6: in 40 synthetic Python projects where the instruction file contradicted the existing code, agents followed the stale file in 90.1% of choices; Claude Code noticed the conflict in 79 of 80 runs and followed the file anyway; Codex rewrote existing code to match in 20 of 80 runs, breaking tests in 17; adding one sentence giving existing code precedence flipped behaviour to 91.4% following the code and restored a 100% test pass rate. Caveat: synthetic single-convention conflicts, two agents, preprint, abstract only read. Implication for a checker: staleness is not a cosmetic issue, a stale rule is actively obeyed.

**Enforcement gap (E8, S4).** Anthropic's docs say instruction files are guidance the model may decide not to follow, and that rules with zero exceptions belong in hooks, deny rules or managed settings. E8 (`unverified`, preprint) reports that only 4.4% (strict) to 16.6% (partial) of security rules found in 481 public CLAUDE.md files have a matching built-in enforceable control (hooks excluded from the count).

### 2.3 llms.txt and docs for agents

**llms.txt v2 (D1).** Location `/llms.txt` or any subpath; a file covers URLs under its path. Order: optional BOM; one H1 (the only required element); a blockquote summary; free Markdown without headings; zero or more H2 sections, each a list of `[name](url)` items optionally followed by `: notes`; an H2 named "Optional" marks links that can be skipped. Pages should expose a clean Markdown twin at `page.md` or `page.html.md` (`index.md` for directory URLs). Discovery through `rel="alternate" type="text/markdown"` and `rel="describedby"` (HTML `<link>` or HTTP `Link` header). It complements robots.txt and is not a sitemap replacement. `llms-full.txt` is not part of the v2 page but is a widespread convention (D4). It is a proposal, not a ratified standard; a claim that Google does not use it is `unverified` (secondary snippet).

**Measured agent behaviour (D2; 1,033 runs, 25 sites, six sites account for 66.9% of runs).** Agents requested Markdown in 65.1% of fetches and chose Markdown 95.7% of the time when naming a format. They reached llms.txt mostly through links (86% of attributed fetches) and 36% of runs that reached it drew the final answer from it, but in controlled probes adding llms.txt did not change whether an answer already present in server-rendered HTML could be retrieved. Sitemaps were fetched in 4% of runs; `.well-known` paths in 22.7%; `openapi.json` in 21% where it existed. 61% of answers containing code included lines copied verbatim from a fetched page. Rules derived: put answers in initial HTML (SSR or prerender); one canonical page per answer; fenced, language-tagged, runnable code blocks; serve `text/markdown` on `Accept: text/markdown` with `Vary: Accept`; advertise mirrors with `Link` headers; real 404s (no soft 404), `429` with `Retry-After` instead of challenge pages; a 403 blocked both tested clients; test with `curl -iL -A 'Claude-User/1.0' <url>`; link llms.txt from pages agents already visit.

**Cloudflare (D3).** Edge conversion of HTML to Markdown on `Accept: text/markdown`; their own post is 16,180 tokens as HTML vs 3,150 as Markdown (80% less); response carries `x-markdown-tokens` and `Content-Signal` headers; Claude Code and OpenCode already send the Accept header.

**Vendor practice.** Stripe (D5): every docs URL has a `.md` twin, an MCP server, an installable skills catalog at `/.well-known/skills/index.json`, and a CLI command that configures the agent. Anthropic and agentskills.io (observed while fetching S3, D6): every Markdown docs page starts with a pointer to the site's `llms.txt` index. Mintlify (D4): slim index plus full export; one-line description after each link; order links by importance; avoid listing every page, generic labels and mirroring internal taxonomy.

**Agent-friendly commands and CLIs.** No authoritative standard was found; the consistent practitioner guidance (community skills and blog posts, `unverified` as primary sources) is: every prompt has a flag/env/stdin equivalent; a structured output mode (`--json`), data on stdout and logs on stderr; 0 on success and distinct non-zero exit codes; stable `--help` treated as contract. This matches what the vendor docs ask of instruction files: exact commands with flags (S9), tool versions and step order, validated commands and known failure workarounds (S5), and a check the agent can run to verify its own work (S4). The kernel's assistant procedure (P4) adds: say explicitly what could not be built or tested.

### 2.4 Agent Skills as a distribution format

**Format (D6).** A skill is a directory with a required `SKILL.md` (YAML frontmatter plus Markdown body) and optional `scripts/`, `references/`, `assets/`. Frontmatter: `name` required, 1 to 64 chars, lowercase `a-z0-9` and hyphens, no leading/trailing/consecutive hyphens, must equal the parent directory name; `description` required, 1 to 1024 chars, says what the skill does and when to use it; optional `license`, `compatibility` (max 500 chars), `metadata` (string-to-string map), `allowed-tools` (space-separated, experimental). Progressive disclosure: about 100 tokens of metadata always loaded, body under 5,000 tokens recommended and under 500 lines, resources loaded on demand. File references are relative to the skill root and one level deep. Anthropic adds (D9): no XML tags in name/description, reserved words `anthropic` and `claude` not allowed in names on its platform, description in third person, table of contents in reference files over 100 lines, forward slashes only, no time-sensitive statements, consistent terminology, list required packages, state whether a script is to be run or read, at least three evaluations.

**Governance and adoption (D8, E5).** Created by Anthropic, released as an open standard, developed in the open at github.com/agentskills/agentskills. Codex and Copilot docs both state they build on it (D10, D11). In the wild (E5, Feb 2026): 601 skills in 158 repos; 85.5% have no bundled resources, about 7.8% ship scripts, 4.8% exceed 500 lines.

**Packaging for several agents (D7, D10, D11).** Put the skill in `.agents/skills/<name>/SKILL.md`: Codex scans it from cwd up to the repo root plus `~/.agents/skills` and `/etc/codex/skills`; Copilot scans `.github/skills`, `.claude/skills` and `.agents/skills` (and `~/.copilot/skills`, `~/.agents/skills`); the client guide recommends every client scan `.agents/skills/` and notes many also scan `.claude/skills/` for compatibility. Claude Code's documented native location is `.claude/skills/<name>/SKILL.md` (S4); whether current Claude Code also scans `.agents/skills/` was not verified (S3 says nothing under `.agents/` is read for instruction files). Practical consequence: keep one real copy and symlink the other location (Codex follows symlinked skill folders). Stay inside the common subset: only `name` and `description` are portable; client extensions live elsewhere (`agents/openai.yaml` for Codex, `disable-model-invocation` for Claude Code). Quote YAML values containing colons (clients differ in leniency). On name collisions project beats user; behaviour within a scope is client-defined. Clients are advised to gate project-level skills behind a workspace trust check. Distribution channels: plugins (Claude Code, Codex), `gh skill`, vendor CLIs, `.well-known/skills/index.json` (Stripe).

### 2.5 CONTRIBUTING and AI-contribution policies

**Classic guidance.** GitHub (C1): `CONTRIBUTING` (case-insensitive, any supported extension) in `.github/`, root or `docs/`, in that precedence; linked when opening issues and PRs, on the `contribute` page, and as a tab and sidebar link when it is `CONTRIBUTING.md`; organisation-wide default via a `.github` repo; use issue and PR templates for per-item guidance. README (C2): `.github/`, root, `docs/` in that precedence; rendered content truncated beyond 500 KiB; prefer relative links (absolute links break in clones); keep the README to what is needed to start using and contributing. Open Source Guides (C3): README answers what the project does, why it is useful, how to get started, where to get help, and states if contributions are not accepted or the project is not production-ready; CONTRIBUTING covers how to file a bug, suggest a feature, set up the environment and run tests, plus the kinds of contributions wanted, roadmap, and how to contact maintainers; link CONTRIBUTING from the README; have LICENSE and CODE_OF_CONDUCT. Mozilla Science Lab (C4): welcome, table of contents, key resources, testing, environment setup, submitting changes (with expected response time), bug reporting, first bugs, feature requests, style guide, code of conduct, recognition, who is involved, where to get help. Contributor Covenant (C5): v3.0 is current; adopt via the builder with a real reporting contact.

**AI-contribution policies: the spectrum.**

| Position | Projects | Key rules |
|---|---|---|
| Total ban, including discussion and assistance | Zig (P9) | No LLM-generated code or prose, no LLM editing, translation, brainstorming results or bug-finding in project spaces |
| Ban on AI-generated content in contributions | Gentoo (P5, 2024-04-14), Servo (P8), QEMU (P7), NetBSD (P6) | Gentoo: copyright, quality, ethics; revisit clause. Servo: also bans AI-written PR summaries, issues and comments; allows translation, verified bug-finding, codebase exploration. QEMU: declines when AI use is "known or suspected" on DCO grounds; research/debugging use allowed if output is not contributed; exceptions by mailing-list request. | Graded, restrictive | Rust (P14, Aug 2026) | LLMs may analyse, check and review but not create; LLM-authored comments, PR descriptions and docs banned; LLM code only as a pre-arranged, non-critical, well-tested experiment with disclosure; lying about use is a CoC violation; pause on new LLM PRs if they exceed 50% of merges in a 6-week window; no style-based accusations |
| Allowed with mandatory disclosure and accountability | Ghostty (P1), LLVM (P3), Linux kernel (P4), Kubernetes (P13), Fedora (P10), curl (P2), Django, SciPy, Cilium (P15, not individually read) | Ghostty: disclose tool and extent, must be able to explain the code without AI, no AI media, PRs only for accepted issues, vouching for first-timers, public denouncement list. LF: treated like any other contribution; projects may add their own rules |

Aggregate numbers: of 118 policies found in 1,000 popular repos, 78% allow AI-assisted contributions, 22% discourage them, 51% require disclosure and 74% require a human in the loop (E9). Only about 12% of popular repos had any AI policy at the time (118 of 1,000).

**Trailers: direct conflict between projects.** `Assisted-by:` is recommended by Fedora (P10, unverified primary) and given as an example by LLVM (P3); the kernel is listed as requiring it by P15, but the exact tag format was not visible in the kernel pages read today (`unverified`). Apache suggests `Generated-by: <tool> <version>` or `Co-authored-by:` (P11). Kubernetes forbids `assisted-by`, `co-developed` and similar trailers and any AI co-author (P13); pip forbids `Co-authored-by:` for AI tools (P15). The kernel forbids agents adding `Signed-off-by`. A checker therefore cannot prescribe one trailer; it can only check that the project states its own rule.

**Security reports.** curl ended its bug bounty on 2026-01-31: confirmed-vulnerability rate fell from 15% or more to under 5% from 2025; 87 confirmed vulnerabilities and over 100,000 USD paid over the programme; reports now go through GitHub private vulnerability reporting or email, no rewards, slop submitters banned (P2). The kernel procedure requires a reproducer, a tested fix, and an explicit statement of what was not verified (P4). Servo, Rust and curl all allow AI-assisted bug finding only if the human verifies and reproduces the finding.

**Workflow gating beyond text policy.** Ghostty: discussion first, issues only when actionable, PRs only for accepted issues, vouch before first PR, automated closing of unvouched PRs (P1). LLVM: `extractive` label and escalation to lock threads (P3). RedMonk notes a growing set of projects that lock down or gate public PR pathways (P16). E10 summarises the driver as review capacity rather than generation.

### 2.6 Prompt injection and supply-chain risks

- Hidden Unicode in rules files (X1, March 2025): zero-width joiners, bidirectional markers and other invisible characters carry instructions that reviewers and GitHub's PR diff did not show; the agent inserts malicious code and omits it from its summary; poisoned rules persist across sessions and forks. Cursor classed it as user responsibility; GitHub added a hidden-Unicode warning on github.com on 2025-05-01.
- README and linked-doc injection (X3, March 2026): direct commands in a README succeeded about 84% of the time and about 91% when placed two links away; 93% of 15 human reviewers failed to identify the attack. Other vectors: Unicode Tags codepoints, instructions in filenames.
- Incidents (X2, Oct 2026): a planted `AGENTS.md` in `~/Downloads` got Codex to install a malicious npm package (stand-in payload ran in over 90% of attempts) and a companion `CLAUDE.md` got Claude Code to redirect API traffic in about half of attempts (reported 2026-10-25/26, no vendor patch at the time); the Miasma worm (2026-06-05) committed `.claude/settings.json`, `.gemini/settings.json`, `.cursor/rules/setup.mdc` and `.vscode/tasks.json` to `Azure/durabletask` under a commit message describing a code change, leading GitHub to disable 73 repositories; CVEs for pre-trust hook/MCP execution in Claude Code (CVE-2025-59536, CVE-2026-21852, patched), Copilot auto-approve (CVE-2025-53773), Cursor project config (CVE-2025-61592) and cross-tool hooks (CVE-2026-48124). CSA's framing: instruction files persuade, settings files execute.
- Skills (X4, Feb 2026): of 3,984 marketplace skills, 36.82% had at least one security flaw, 13.4% a critical one, 76 were confirmed malicious, and 91% of malicious skills used prompt injection in the SKILL.md prose itself.

Hygiene rules that follow (X1, X2, X3, D7): treat instruction, rules, skill and agent-settings files as executable code in review; CODEOWNERS entries for them; reject zero-width, bidirectional and Unicode Tags characters in pre-commit and CI; no instruction to disable approvals or sandboxing, change API endpoints, or install packages from URLs; keep security prohibitions in enforced controls (permissions, hooks, sandbox, egress allow-lists) and reserve prose for conventions that are safe to ignore; do not launch agents in `~/Downloads` or home directories; keep long files reviewable (a single malicious line hides in a long file); be suspicious of commits that touch agent config while describing something else; treat third-party README content as data, not instructions.

### 3.4 Disagreements between sources

1. Architecture and project-structure overviews. For: agents.md lists "project overview"; GitHub docs and blog ask for layout and structure; in practice 68% of files describe architecture and 59% give a system overview (E3). Against: Anthropic says not to describe architecture or file layout; E1 found overviews did not shorten the path to the relevant files. Possible reconciliation: allow only non-inferable structure (where generated code lives, which directories are off-limits).
2. Do context files help at all. E1: no significant success gain, about 20% more cost. E2: 28.6% lower runtime and 16.6% fewer output tokens. Vendors all recommend them. The studies measure different things on small samples; none measures convention adherence, which is the main stated purpose.
3. LLM-generated files. Claude Code `/init` and GitHub's onboarding prompt generate them; E1 recommends omitting LLM-generated files. Possible reconciliation: generate, then delete everything redundant with existing docs.
4. Length. Under 200 lines (Anthropic), under 500 lines per rule (Cursor), 2 pages (Copilot onboarding prompt), 32 KiB hard cap (Codex), about 500 lines in some linters; E1 found no clear correlation between length and success or cost. Observed medians are far below these limits (335 to 535 words).
5. Emphasis and trust. GitHub docs suggest "always" wording and telling the agent to trust the instructions; Anthropic says emphasis is counterproductive with current models; E6 shows unconditional trust in the file is harmful when it is stale and proposes the opposite sentence (existing code takes precedence).
6. Commands in the file. All sources but one ask for commands; Cursor says not to document common commands. Reading: document project-specific commands and flags, not what any agent already knows.
7. AI attribution trailers. `Assisted-by` (Fedora, LLVM example, kernel per P15) vs `Generated-by` or `Co-authored-by` (ASF) vs trailers and AI co-authors forbidden (Kubernetes, pip). Disclosure location also differs (commit trailer vs PR description).
8. AI use for non-code text. Allowed after human editing (Ghostty), banned for PR descriptions and comments (Servo, Rust, Kubernetes for review replies and commit messages), translation allowed (Servo, Rust with disclosure) vs banned (Zig).
9. Nesting semantics. "Nearest file wins" (agents.md, Copilot), "concatenate, later overrides" (Codex), "combined, more specific wins" (Cursor), "all loaded, conflicts resolved arbitrarily" (Claude Code). A portable file set must therefore avoid relying on override behaviour: nested files should add, not contradict.
10. llms.txt value. Promoted by the proposal and docs vendors; D2 found it rarely changes retrieval when the HTML is already good, though agents that reach it use it.

## 4. Open questions and weak evidence

- No study measures whether instruction files improve adherence to project conventions, security or maintainability; E1 measures only task success, steps and cost on Python bug-fix tasks, with non-significant success differences.
- E1 vs E2 conflict on cost/efficiency is unresolved; E2, E6 and E7 were read at abstract level only, and E6, E7, E8 are unreviewed preprints. E8 was not read at all (`unverified`).
- Benchmark name in E1 (CTXbench in the v3 text fetched vs AGENTbench in secondary coverage of v1) and the "7%" figure in its introduction vs the 2.4-point result should be rechecked against the PDF.
